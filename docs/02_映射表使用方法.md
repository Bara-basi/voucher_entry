# 映射表使用方法

## 平台档案

`mappings/platform/`中的客户、供应商、存货、科目、人员、项目、银行账号JSON主要使用`records`数组。编码用于模板，内部`id`用于接口；两者不能混用。`名称编码索引.json`方便反查，但一个名称可以对应多个候选，不能简单取第一条。

会计科目应选叶子科目，并结合`科目辅助核算配置.json`检查是否要求客户、供应商或存货等信息。存货需同时核对产品名称、计量单位、库存科目。`凭证及账簿基础配置.json`保存账簿、币种、凭证类别、汇率类型等参考。所有平台档案是2026-10-14当前登录账号可见范围的快照，不包含未来变更，也不保证覆盖已删除或无权限档案。

## 客户

优先级：人工已确认别名 → 既有唯一解析记录 → 当前档案规范化唯一匹配 → 编辑距离候选供复核。

- `customer_alias_mappings.json`：人工已确认别名到平台编码的映射。
- `customer_resolution_history.json`：此前唯一解析的记录，保留来源证据；人工别名优先。
- `scripts/customer_matching.py`：名称规范化、人工映射及历史映射查询、候选权重辅助函数；不是独立的候选表生成程序。
- 客户编码末尾“-”表示财务常用候选；当前排序规则增加0.05权重。此规则用于排序，不能覆盖已确认映射，也不能凭此对低相似候选直接下结论。
- 代码作为字符串保存，不删除“-”或前导0。飞书业务客户编号不等于用友档案编码。

Shchekinoazot Chemical Company到ООО «НПО РИЗУР» / OOO NPO RIZUR属于用户查历史凭证后确认的业务对应关系，不能自动推广成翻译或名称相似规则。

## 供应商

`finance_supplier_alias_mappings.json`使用`mappings`数组，记录财务简称→用友编码/全称及依据；`supplier_directory_snapshot.json`保留供应商名录原始参考。通常路径是财务副本供应商简称→名录全称→用友唯一档案。无供应商或存在歧义仍记异常，不做订单白名单。

## 产品类型

`finance_product_types_snapshot.json`是财务副本“产品及类型”表及字段元数据。产品类型可能返回`opt...`选项ID，应按`fields[].property.options`的`id/name`解码，再使用`records[].fields`中的关联值。它是分组参考，不等于用友存货编码；“其他”等分类过粗，不能直接绑定单一存货。

## 业务主表口径

以财务副本“2026年报关数据”的拆单行为金额和成本来源；出运单采用`合同号_1`。关联字段`合同号`可能指向成本来源订单，不可将二者无条件混合匹配。

AI表“客户名称_脚本用”只补客户名。按报关单关联时若多个名字冲突，应列异常，不随意择一。当前任务范围为出口日期2026-01-01至2026-09-30、销售方式出口，排除25MT/CY/25SM/26SM前缀；缺客户名另列待补。AI表金额与供应商不能反向替代财务主表。
